# Vibe Code Plan: как начать разработку Telegram-бота для YouTube-авторов

## Цель плана

Сделать так, чтобы можно было открыть этот файл и сразу понимать:

- с чего начать;
- какой стек выбрать;
- как разложить фичи;
- как тестировать;
- где будут расходы;
- какие модели использовать;
- какие навыки понадобятся Codex и тебе;
- как за 1-2 недели собрать MVP для теста на учениках.

## Короткий технический выбор

Так как ты предпочитаешь Go, я бы начинал на Go.

Почему Go подходит:

- простой деплой одним бинарником;
- хорошо держит Telegram webhooks и фоновые задачи;
- легко писать чистую серверную логику;
- удобно контролировать расходы, лимиты и очереди;
- меньше магии, чем в больших фреймворках.

Java тоже подойдет, особенно если ты ее учишь, но для быстрого MVP Telegram-бота я бы не начинал со Spring Boot, если нет сильной причины. Spring мощный, но для первой версии будет больше инфраструктурного веса. Java можно использовать позже, если проект вырастет или если тебе принципиально тренироваться именно в Java.

Рекомендация:

- MVP: Go.
- Если хочется учить Java параллельно: сделать отдельные маленькие упражнения или позже переписать один сервис.

## Стек MVP

- Язык: Go.
- Telegram: библиотека для Telegram Bot API, например `github.com/go-telegram/bot` или `gopkg.in/telebot.v3`.
- База данных: PostgreSQL.
- Векторный поиск: pgvector внутри PostgreSQL.
- Миграции: `goose` или `golang-migrate`.
- Конфиг: `.env` локально, переменные окружения на сервере.
- Логи: `slog` из стандартной библиотеки Go.
- Очереди: на MVP можно без очереди; позже Redis + worker.
- Хостинг MVP: VPS, Render, Railway, Fly.io или аналог.
- Локальная разработка: Docker Compose для Postgres.
- Админка MVP: можно начать без UI, через SQL/логи; позже сделать простую web-админку.

## Почему нужен хостинг

Telegram-бот должен где-то постоянно работать.

Локально можно разрабатывать через long polling, но пользователи не смогут нормально пользоваться ботом, пока твой компьютер выключен.

Для beta нужен сервер:

- VPS или PaaS;
- домен не обязателен для long polling;
- домен и HTTPS нужны для webhook;
- база данных должна жить отдельно или на том же VPS в Docker.

Рекомендация:

- Локально: long polling.
- Для первых 5-10 тестеров: можно long polling на VPS.
- Для нормального запуска: webhook + HTTPS.

## Общая архитектура

```
Telegram
  -> Bot Handler
  -> Use Cases
  -> AI Gateway
  -> YouTube Data Gateway
  -> Knowledge Base
  -> PostgreSQL
  -> Background Jobs
```

Главные слои:

- `bot`: принимает сообщения и кнопки Telegram.
- `app`: бизнес-логика: онбординг, анализ, идеи, сценарии, платежи.
- `ai`: единый интерфейс к OpenAI/Anthropic/Gemini.
- `youtube`: получение данных канала и роликов.
- `knowledge`: поиск по базе знаний.
- `storage`: работа с PostgreSQL.
- `billing`: подписки, кредиты, списания.
- `admin`: отчеты по пользователям и расходам.

## Какие внешние API нужны

### Telegram Bot API

Нужен для самого бота, кнопок, сообщений и оплат.

Для цифровых услуг внутри Telegram стоит учитывать Telegram Stars. В Bot API для Stars используется валюта `XTR`, а для подписки `subscription_period` сейчас должен быть 30 дней. Источник: https://core.telegram.org/bots/api#sendinvoice

### YouTube Data API

Нужен для анализа канала и роликов.

Важно: YouTube Data API имеет дневные квоты. По официальной документации, у проектов с YouTube Data API базово 10 000 units/day, а каждый запрос стоит хотя бы 1 unit. Источник: https://developers.google.com/youtube/v3/determine_quota_cost

Что брать:

- данные канала;
- описание канала;
- список последних видео;
- названия;
- описания;
- просмотры;
- даты публикаций;
- статистику видео;
- плейлисты при необходимости.

На MVP не нужно просить API-ключ пользователя. Лучше начать с открытых данных через свой YouTube API key. Просьба “дай свой API key” может пугать пользователей и усложнит безопасность. Если позже нужен доступ к приватной аналитике канала, лучше делать OAuth.

### AI APIs

Нужен отдельный слой `AI Gateway`, чтобы можно было менять модели без переписывания бота.

Провайдеры:

- OpenAI: тексты, reasoning, изображения, embeddings.
- Anthropic Claude: сильные длинные сценарии и редактура.
- Google Gemini: дешевые массовые задачи, анализ больших контекстов, альтернативный провайдер.

### Web search / research

Для конкурентного ресерча можно:

- сначала использовать YouTube Data API;
- позже добавить web search API: OpenAI Web Search, Tavily, SerpAPI, Google Custom Search или другой источник.

OpenAI Web Search на официальной странице pricing указан как отдельный инструмент с ценой за 1k calls. Источник: https://openai.com/api/pricing/

## Модели: стартовая рекомендация

Цены и названия моделей быстро меняются, поэтому их нельзя зашивать в код. Нужно хранить в конфиге:

- модель для дешевых задач;
- модель для качественных сценариев;
- модель для анализа;
- модель для картинок;
- модель для embeddings.

### Дешевые задачи

Для классификации, коротких ответов, роутинга, резюме и простых генераций:

- OpenAI GPT-5.4 mini или аналогичная mini-модель;
- Claude Haiku 4.5;
- Gemini Flash.

Задачи:

- понять интент пользователя;
- выбрать следующий шаг;
- коротко суммаризировать данные;
- переписать текст;
- сгенерировать варианты названий;
- ответить на простой вопрос.

### Анализ канала и конкурентов

Для первичного анализа:

- GPT-5.4 mini / GPT-5.4;
- Claude Sonnet 4.5 или актуальный Sonnet на момент запуска;
- Gemini 3 Flash/Pro, если нужен дешевый большой контекст.

Подход:

- сначала собрать структурированные данные;
- потом дать модели не “весь интернет”, а компактный JSON/markdown;
- ответ просить в фиксированном формате;
- сохранять итог анализа в базе, чтобы не пересчитывать каждый раз.

### Сценарии

Для сценариев нужна модель лучше, чем для простых задач:

- Claude Sonnet 4.5 или актуальный Sonnet как сильный кандидат для длинных текстов;
- GPT-5.4 как универсальный кандидат;
- Opus/Pro-модели только для дорогого тарифа или финальной редакторской версии.

Логика экономии:

- черновик сценария делать Sonnet/GPT large;
- улучшение/сокращение делать mini;
- не генерировать полный сценарий, если пользователь попросил только план.

### Превью и картинки

Для MVP можно сначала делать не генерацию картинки, а генерацию ТЗ для превью:

- идея;
- композиция;
- текст;
- эмоция;
- фон;
- элементы;
- промпт для генератора.

Для платной версии:

- актуальная image-модель из OpenAI API, выбранная по цене и качеству на момент запуска;
- альтернативно Gemini image model, если цена/качество лучше.

OpenAI указывает отдельное ценообразование для изображений и image tokens. Источник: https://openai.com/api/pricing/

Важно: генерация картинок должна быть отдельным лимитом, потому что она быстро съедает маржу.

### Embeddings и база знаний

Нужны для RAG: бот отвечает не просто из модели, а на основе ваших методичек.

Подход:

- загрузить методички в `knowledge`;
- нарезать на чанки;
- посчитать embeddings;
- хранить в pgvector;
- при запросе искать релевантные куски;
- передавать модели только найденные фрагменты.

На старте можно использовать OpenAI embeddings или другой дешевый embedding-провайдер. Главное - спрятать это за интерфейсом, чтобы можно было заменить.

## Токеномика MVP

Не начинай с точной экономики “по ощущениям”. Сначала сделай таблицу фактических расходов.

Сущности:

- действие;
- модель;
- входные токены;
- выходные токены;
- цена;
- пользователь;
- дата;
- feature.

Пример кредитов:

- простой вопрос: 1 кредит;
- генерация названий: 2 кредита;
- анализ идеи: 3 кредита;
- сценарий-план: 5 кредитов;
- полный сценарий: 10-15 кредитов;
- анализ канала: 20 кредитов;
- анализ конкурентов: 20-40 кредитов;
- генерация картинки: 30-60 кредитов.

Гипотеза тарифов:

- тест: вручную выдать 100-200 кредитов;
- базовый 2 990 рублей: текстовые функции и ограниченные анализы;
- расширенный: плюс картинки;
- pro: больше лимитов и приоритетные модели.

Главное: кредиты для пользователя должны быть простыми, а внутренняя себестоимость должна считаться детально.

## Порядок разработки фич

### Шаг 1: Пустой бот

Сделать:

- создать бота через @BotFather;
- поднять Go-проект;
- принять `/start`;
- отправить приветствие;
- показать главное меню;
- настроить `.env`.

Готово, если: бот отвечает тебе в Telegram.

### Шаг 2: Состояния пользователя

Сделать:

- таблица пользователей;
- таблица состояний диалога;
- обработка кнопок;
- сохранение шага онбординга.

Готово, если: бот помнит, что пользователь уже отправил ссылку или находится на вопросе про ЦА.

### Шаг 3: Онбординг

Сделать:

- приветствие;
- сбор ссылки на канал;
- сбор ЦА;
- сбор цели канала;
- сбор конкурентов;
- сохранение профиля.

Готово, если: в базе есть профиль автора.

### Шаг 4: YouTube Data API

Сделать:

- подключить Google Cloud project;
- включить YouTube Data API;
- научиться доставать данные канала;
- научиться доставать последние видео;
- сохранить сырой JSON и нормализованные данные.

Готово, если: по ссылке на канал бот получает название, описание и последние ролики.

### Шаг 5: AI Gateway

Сделать:

- интерфейс `Generate`;
- провайдер OpenAI;
- провайдер Anthropic или Gemini позже;
- логирование токенов и примерной цены;
- таймауты и retries.

Готово, если: можно одной функцией вызвать модель из любой фичи.

### Шаг 6: Анализ канала

Сделать:

- промпт `channel_analysis.md`;
- собрать данные канала в компактный формат;
- получить анализ;
- сохранить анализ в базе;
- отправить пользователю.

Готово, если: пользователь получает осмысленную диагностику.

### Шаг 7: База знаний v0

Сделать сначала без векторов:

- положить методички в markdown;
- руками подмешивать нужные документы в промпт;
- проверить качество.

Потом:

- добавить embeddings;
- добавить pgvector;
- искать релевантные куски автоматически.

Готово, если: ответы используют вашу методологию, а не общие советы.

### Шаг 8: Анализатор идей

Сделать:

- кнопка “Анализатор идей”;
- пользователь вводит идею или просит идеи;
- бот берет профиль автора и анализ канала;
- выдает карточки идей.

Готово, если: идеи явно связаны с каналом пользователя.

### Шаг 9: Сценарии

Сделать:

- выбрать идею;
- выбрать формат: план/структура/полный сценарий;
- сгенерировать сценарий;
- сохранить проект ролика.

Готово, если: пользователь может пройти от идеи до сценария.

### Шаг 10: Название, описание, теги

Сделать:

- взять идею/сценарий;
- выдать варианты названий;
- описание;
- теги;
- закрепленный комментарий.

Готово, если: ролик можно почти сразу переносить в YouTube Studio.

### Шаг 11: Свободный вопрос

Сделать:

- режим диалога;
- подмешивание профиля пользователя;
- подмешивание базы знаний;
- ограничение на YouTube-тематику.

Готово, если: бот отвечает как методолог по YouTube, а не как общий чат.

### Шаг 12: Лимиты и кредиты

Сделать:

- таблица баланса;
- списание кредитов за действия;
- отказ, если кредитов не хватает;
- админское пополнение.

Готово, если: можно дать 10 тестерам лимиты и не бояться бесконечных расходов.

### Шаг 13: Оплата

Сделать:

- выбрать схему: Telegram Stars или внешний платеж;
- реализовать invoice;
- активировать подписку;
- продление;
- статусы платежей.

Для цифрового продукта внутри Telegram Stars выглядят самым нативным вариантом. Но для российского рынка нужно отдельно проверить юридику, вывод средств, комиссии, привычность оплаты и альтернативы вроде YooKassa/CloudPayments через внешнюю страницу.

### Шаг 14: Превью

Сначала:

- ТЗ на превью;
- промпт для генерации;
- варианты текста на обложку.

Потом:

- загрузка фото;
- генерация изображения;
- отдельный лимит на картинки.

## Как тестировать

### Ручные тесты

Сделать файл сценариев:

- новый пользователь;
- пользователь прислал плохую ссылку;
- пользователь прислал канал;
- пользователь пропустил конкурентов;
- пользователь просит идеи;
- пользователь просит полный сценарий;
- у пользователя закончились кредиты.

### Unit-тесты

Писать на:

- парсинг YouTube-ссылок;
- расчет кредитов;
- переходы состояний;
- форматирование промптов;
- обработку ошибок API.

### Integration-тесты

Писать на:

- storage + PostgreSQL;
- AI Gateway с mock-провайдером;
- YouTube Gateway с сохраненными fixture JSON.

### Prompt-тесты

Нужны обязательно.

Для каждого промпта хранить:

- вход;
- ожидаемый стиль ответа;
- критерии качества;
- плохие примеры.

На старте можно тестировать руками. Позже сделать eval-скрипт, который гоняет 10-20 кейсов и сохраняет ответы.

## Что просить у Codex по шагам

Для разработки лучше давать Codex маленькие задачи.

Примеры хороших запросов:

- “Создай Go-проект Telegram-бота с `/start` и конфигом из env.”
- “Добавь PostgreSQL и миграции для пользователей, профилей и состояний.”
- “Сделай парсер ссылок YouTube-канала и unit-тесты.”
- “Добавь YouTube Data API client, который по channel id получает последние 20 видео.”
- “Сделай AI Gateway с OpenAI provider и mock provider для тестов.”
- “Добавь фичу анализа канала на основе промпта из `/prompts/channel_analysis.md`.”
- “Добавь систему кредитов и списания за действия.”

Не просить сразу:

- “Сделай всего бота целиком.”

Так Codex может расползтись по архитектуре и сделать слишком много ненужного. Лучше идти фичами.

## Риски

- Бот будет отвечать слишком общо, если нет методологии.
- Расходы улетят, если не поставить лимиты.
- YouTube API квота закончится, если делать слишком много запросов.
- Генерация картинок может съесть маржу.
- Пользователи могут не понимать, что вводить, если онбординг слабый.
- Слишком ранняя оплата может замедлить тестирование.
- Слишком сложная архитектура убьет скорость MVP.

## Первые конкретные действия прямо сейчас

3. Получить Telegram bot token через @BotFather.

7. Получить Google Cloud API key для YouTube Data API.
8. Получить OpenAI API key.
9. Сделать первый анализ канала по одной ссылке.
